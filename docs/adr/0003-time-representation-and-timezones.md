# ADR-0003 — Store UTC instants, evaluate policy in the resource's local timezone

- **Status:** Accepted
- **Date:** 2026-11-10

## Context

"Mon–Fri 8am–5pm Pacific" is a statement about local civil time. Pacific time
shifts by an hour twice a year; on those days a naive fixed-offset
implementation either opens an hour early, closes an hour late, or generates a
slot that does not exist. Meanwhile, the overlap invariant is a statement about
absolute instants. Conflating the two is the classic source of scheduling bugs.

## Decision

Three rules:

1. **At rest:** every timestamp is `timestamptz` (a UTC instant). Availability
   rules store a weekday and a *local* `time` plus the resource's IANA timezone
   (`America/Los_Angeles`) — never a numeric offset.
2. **On the wire:** RFC 3339 with an explicit offset, both directions. Inputs
   without an offset are rejected (422) rather than assumed.
3. **In logic:** slots are generated by walking local civil days in the
   resource's `time.Location`, constructing local wall-clock times, then
   converting to instants. Overlap and storage are compared as instants only.

Timezone is a property of the resource, not a server constant. All intervals are
half-open `[start, end)`.

DST edge cases are explicit test fixtures: the spring-forward day (a local hour
that does not exist — those slots are skipped) and the fall-back day (a local
hour that occurs twice — each occurrence is a distinct instant and both are
offered if policy allows).

## Alternatives considered

| Option | Why not |
|---|---|
| Store local wall-clock time only | Overlap comparison becomes ambiguous exactly when it matters most (fall-back). |
| Store a fixed `-08:00` offset | Wrong for roughly eight months of the year. |
| Normalise everything to UTC including policy | "8am Pacific" is not a fixed UTC time; the rule drifts by an hour seasonally. |
| Server-wide timezone constant | Blocks a second region, and makes the correct behaviour depend on deployment config. |

## Consequences

**Positive** — correct across DST and across regions; comparisons are
unambiguous; multi-region resources are already supported.

**Negative / accepted costs** — slot generation is more intricate than
arithmetic on UTC; the service image must ship the tzdata database
(`go build -tags timetzdata` or the tzdata package in the container).

**Revisit when** — never, realistically. This is the conservative choice.
