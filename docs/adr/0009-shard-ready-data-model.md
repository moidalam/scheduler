# ADR-0009 — Shard-ready schema from day one, on a single node

- **Status:** Accepted
- **Date:** 2026-11-10
- **Relates to:** ADR-0002, ADR-0004, ADR-0008
- **Amends:** ADR-0008 (identifier generation)

## Context

The service starts on one PostgreSQL instance. It is expected to face data
growth large enough that a single node will not hold it, so a design that can
only ever run on one node is not acceptable.

Sharding cannot be bolted on later cheaply. Three things in particular are
near-impossible to retrofit once there is production data:

1. **The shape of primary keys.** Every hash-sharded system requires the
   distribution column inside every primary key and unique constraint. Adding
   a leading column to a live PK means rewriting that table and every foreign
   key that references it, across every node.
2. **The identifier scheme.** Node-local sequences collide the moment there are
   two writers.
3. **The number of logical shards.** Changing the hash space rehashes every row.

Each of these costs nothing to get right now. Everything else about sharding —
running a coordinator, operating many nodes, rebalancing — can wait and should.

## Decision

**Design the schema to satisfy a distributed Postgres from the start, and
deploy it on a single ordinary node.** No extension is installed, no
coordinator is run, no operational cost is taken on today. What we take on is a
set of constraints the schema must obey, which a single node accepts happily.

### 1. The distribution key is `resource_id`

Chosen because the system's hot paths are already scoped to one resource:

| Operation | Shards touched |
|---|---|
| Generate availability for a resource | 1 |
| Create a booking | 1 |
| List a resource's bookings | 1 |
| Enforce no-overlap (ADR-0004) | 1 |

This is the decisive property. The no-overlap invariant is defined *per
resource*, so every booking that could conflict with another lives on the same
node, and the exclusion constraint stays a local constraint. We never need a
distributed lock or a two-phase commit to protect the one invariant that must
never fail.

`tenant_id` was the obvious alternative and is rejected: a single large tenant
(a national gym chain) would pin an unbounded amount of data to one node, which
is the hotspot sharding exists to avoid. `resource_id` gives far finer grain.

### 2. Every table is classified, and the class is part of the schema

| Class | Tables | Rule |
|---|---|---|
| **Distributed** by `resource_id` | `bookings`, `availability_rules`, `availability_exceptions`, `booking_events` | Co-located: a resource's rows all live together. |
| **Distributed** by its own `id` | `resources` | Co-located with the above, since `bookings.resource_id = resources.id`. |
| **Distributed** by lookup value | `resource_aliases`, `bookings_by_requester` | Secondary-index tables; see §4. |
| **Reference** (replicated to every node) | `services`, `tenants` | Small, bounded, read-mostly, joinable from anywhere. |

A table may not change class without a migration, so the class is recorded in
the data model next to each table.

### 3. Keys always contain the distribution column

```sql
-- bookings
PRIMARY KEY (resource_id, id)
UNIQUE      (resource_id, idempotency_key)
EXCLUDE USING gist (resource_id WITH =, tstzrange(...) WITH &&)
```

This is valid, useful SQL on a single node today — the composite key costs
nothing — and it is the exact shape a distributed table requires.

Note the consequence for uniqueness: `UNIQUE (resource_id, external_id)` does
**not** guarantee a booking's public id is unique globally. We rely instead on
the identifier being a 122-bit random UUID (§5), where collision is not a
practical concern. Where global uniqueness must actually be *enforced* rather
than assumed, the table is a reference table or carries a secondary-index table.

### 4. Lookups that do not carry the distribution key get an index table

A query that cannot name a `resource_id` must otherwise ask every node. Two
such lookups exist, and each gets its own table distributed by the value being
looked up — two single-shard hops instead of one fan-out:

- **`resource_aliases`** — maps a legacy or alternate public identifier
  (`"1"`, from the seed data) to a `resource_id`. Distributed by `alias`.
- **`bookings_by_requester`** — maps a requester to their bookings, for "show
  me all my appointments across trainers". Distributed by `requester_id`, and
  written through a transactional outbox rather than a cross-shard transaction,
  so it is eventually consistent by design.

### 5. Identifiers are UUIDv7, generated by the application

Supersedes the open question in ADR-0008 §3, which specified how a *supplied*
identifier is recorded but never said what to mint for an entity created here.

- Internal keys and new public identifiers are **UUIDv7** — time-ordered, so
  index inserts stay local instead of scattering the way UUIDv4 does, and
  requiring no coordination between writers.
- Generated **in the application**, not as a column default, so the id is known
  before the insert and can be written into logs, the outbox row, and the audit
  event inside one transaction. A `DEFAULT` remains on the column as a
  backstop against a direct SQL insert producing a NULL.
- Public ids carry a **type prefix** — `res_`, `bkg_`, `svc_` — so a booking id
  passed where a resource id belongs fails immediately and legibly instead of
  returning a confusing 404.
- Node-local sequences (`bigserial`) are rejected: they collide across writers,
  which is the whole point.

### 6. Logical shards are fixed high now

`resource_id` hashes into **65536 logical shards**, mapped many-to-one onto
physical nodes. Growing the fleet moves logical shards between nodes; it never
rehashes a row. The count is chosen once and generously because changing it
later is a full data migration. On one node, all 65536 map to that node and the
number is invisible.

### 7. No cross-shard foreign keys, no cross-shard transactions

A foreign key may point only at a co-located distributed table or a reference
table. A write transaction may touch only one resource's data. This forbids a
booking that reserves two resources at once — already a non-goal (PRD §4), now
also a structural constraint, and the reason ADR-0001's "revisit when" trigger
is a genuinely expensive change rather than a schema tweak.

## Alternatives considered

| Option | Why not |
|---|---|
| Single-node schema now, shard when needed | The three items in Context cannot be retrofitted cheaply. This is the decision being rejected. |
| Adopt Citus / Aurora Limitless now | Real operational cost — coordinator, many nodes, rebalancing — bought years before any benefit. The schema discipline is what has to be early; the infrastructure does not. |
| Shard by `tenant_id` | Hotspots on large tenants, and no help with the overlap invariant. |
| Shard by time (`starts_at`) | Breaks the overlap invariant at boundaries, since one resource's bookings scatter across shards. Disqualifying. |
| CockroachDB / YugabyteDB from the start | Distributed by default, but not Postgres — we lose `tstzrange` exclusion constraints (ADR-0004) and the ecosystem, to solve a problem we do not yet have. |
| Application-level sharding with `bigserial` plus per-node ranges | Workable, but every writer must be allocated a range by a coordinator, and a misconfigured node silently duplicates ids. |

## Consequences

**Positive** — one node today with no extension, no coordinator and no added
operations; the growth path is `create_distributed_table('bookings',
'resource_id')` rather than a schema rewrite; the overlap invariant survives
sharding intact; the design is portable across Citus, Aurora Limitless, and
hand-rolled sharding, because all three impose these same rules.

**Negative / accepted costs**
- Composite keys are wordier, and every query must carry a `resource_id` to
  stay single-shard. This is a discipline the team must hold *before* there is
  any feedback telling them they broke it — the main risk of this decision.
- `GET /v1/bookings/{id}` cannot be served without a `resource_id`, so the
  route is nested under the resource (ADR-0006 amended accordingly).
- Requester-centric reads are eventually consistent (§4).
- Global uniqueness of public ids is probabilistic rather than enforced (§3).
- Two extra tables exist purely to serve lookups.
- We carry all this against growth that may never arrive. The cost is small and
  paid once; the alternative is a migration under load.

**Must verify before implementation** — whether the target distributed
Postgres accepts an **exclusion constraint** on a distributed table. ADR-0004's
guarantee depends on it. If it does not, the invariant needs a different
mechanism at scale and this ADR must be revisited. Tracked as API-12 in the
risk register. The same question applies to declarative partitioning, where
exclusion constraints on a partitioned parent are understood to be unsupported.

**Revisit when** — the shard key needs to change, which is the one thing this
design still makes expensive.
