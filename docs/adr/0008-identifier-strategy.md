# ADR-0008 — Opaque string identifiers in public APIs, UUID keys internally

- **Status:** Accepted, amended by ADR-0009
- **Date:** 2026-11-10
- **Relates to:** ADR-0001, ADR-0006
- **Amended by:** [ADR-0009](0009-shard-ready-data-model.md) §5 — this ADR
  specified how a *supplied* identifier is recorded but never said what to mint
  for an entity created here, which left `bookings.external_id` NULL for every
  booking created through the API. ADR-0009 fixes that: application-generated,
  type-prefixed UUIDv7.

## Context

The system's identifiers must satisfy two constituencies at once.

The data we are given uses **integers**: `appointments.json` has integer `id`,
`trainer_id`, and `user_id`, and the brief's first endpoint takes a
`trainer_id`. Whatever is in that file is what real callers already hold; an API
that cannot accept `1` cannot serve them.

Meanwhile, the service is deliberately domain-agnostic (ADR-0001). A second
domain's resources and requesters will arrive with their own identifier scheme —
UUIDs, ULIDs, vendor strings — and will not be integers. Sequential integers in
a public contract also leak volume and invite enumeration.

The first draft of these specs picked `format: uuid` for every public id without
reconciling it against the seed file. That was an unforced error: it made the
brief's own example call invalid, and the integer→UUID mapping it implied was
asserted in prose but had nowhere to live in the schema.

## Decision

Separate the public identifier from the storage key.

1. **Public ids are opaque strings.** The OpenAPI contract types every
   identifier as `type: string` with no `format`. `"1"` and
   `"7b1f3c2e-..."` are both valid. Clients must treat ids as opaque —
   never parse, order, or do arithmetic on them.
2. **Storage keys stay UUIDs.** `resources.id`, `services.id`, `bookings.id`
   remain `uuid`, generated by us. This keeps joins uniform and keeps our
   internal keys independent of anything a caller supplies.
3. **The incoming identifier is recorded, not derived.** Entities that
   originate elsewhere carry an `external_id` column holding the caller's own
   identifier verbatim as `text`, unique per tenant. The integer `1` is stored
   as the string `"1"`.
4. **Resolution accepts either form.** An id in a request path or body is
   matched against `external_id` first, then against the UUID key. One lookup,
   either shape, no separate endpoints.
5. **Responses echo the form the caller uses.** A caller who addresses a
   resource by `"1"` sees `"1"` in the response body, so round-tripping a
   booking object works without translation.

`requester_id` is not an entity this service owns (PRD R-4), so it is stored
directly as `text` on the booking — the value the caller sent, not a surrogate.

## Alternatives considered

| Option | Why not |
|---|---|
| UUIDs everywhere, including public ids | Breaks the brief's `trainer_id` call outright and strands the existing data. The rejected first draft. |
| Integer ids throughout, matching the seed exactly | Simplest and exactly what the exercise shows, but bakes sequential public ids into a service meant to outlive this product, leaks row counts, and forces every later domain to mint integers it does not have. |
| UUIDs public, with a separate `/resolve?trainer_id=` endpoint | An extra round trip on the hot path, and every client must learn a two-step dance. |
| Derive a UUIDv5 from the integer and expose that | The mapping is reproducible but invisible: nobody can answer "which resource is trainer 2?" without re-running the derivation. Fails operationally. |

## Consequences

**Positive** — the supplied data works unmodified; the brief's endpoints are
callable as written; a second domain brings its own ids without a migration;
internal keys stay uniform; the mapping is queryable data rather than a
convention.

**Negative / accepted costs** — the API gives up the validation that
`format: uuid` provided, so a malformed id surfaces as `404` rather than `400`;
resolution is one indexed lookup rather than a direct primary-key hit; two
notions of identity now exist and documentation must keep them distinct. The
`external_id` uniqueness constraint is per tenant, so collisions across tenants
are permitted by design.

**Revisit when** — a caller needs to change an entity's `external_id` while
keeping its history, which would make the "responses echo the caller's form"
rule ambiguous.
